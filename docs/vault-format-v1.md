# Buddy vault format v1

This document defines the cryptographic and persisted-data contract needed to
open a Buddy Password Manager vault without the commercial desktop
application. It describes the current SQLite schema and external attachment
layout, but not UI behavior, licensing, analytics, imports from other password
managers, or operating-system biometric key storage.

The profile identifier used by the compatibility fixtures is
`buddy-vault-v1`. The reference implementation is `buddy-crypto-core`.

## Conventions

The words MUST, MUST NOT, SHOULD, and MAY describe interoperability
requirements.

- Byte strings in SQLite are stored as raw `BLOB` values. Attachment
  ciphertext is stored as raw file bytes.
- Hexadecimal is only a presentation encoding used by the published test
  vectors. Its exact rules are defined in
  [`../test-vectors/README.md`](../test-vectors/README.md).
- Passwords and encrypted JSON plaintexts use UTF-8 without a byte-order mark
  or trailing NUL.
- XChaCha20-Poly1305 ciphertext is `ciphertext || tag`, where the tag is the
  final 16 bytes. The verifier and attachment content use empty associated
  data. Entry payloads and attachment-key envelopes authenticate the record
  context defined below.
- All production salts, keys, verifier plaintexts, and nonces described as
  random MUST be generated by an operating-system cryptographically secure
  random number generator.
- A nonce is 24 bytes and MUST NOT be reused with the same XChaCha20-Poly1305
  key. Buddy generates a fresh random nonce for every encryption.
- IDs are UTF-8 strings and should be treated as opaque. Current writers use
  UUID strings.
- Persisted timestamps are signed Unix timestamps in seconds.

JSON object member order is not semantically significant. Current Buddy
writers emit compact JSON with no insignificant whitespace, but readers MUST
accept any valid JSON representation of the documented payload. Re-serializing
equivalent JSON can therefore produce different ciphertext without changing
the logical entry.

## Version spaces

Three version numbers exist independently:

- `buddy-vault-v1` is the cryptographic and logical vault profile.
- Application migration numbers form one ordered history. The `migrations`
  table records each migration's application-wide portion, while
  `vault.version` records the last migration applied to that individual vault.
  The schema and vault data in this document are migration `1`.
- The Rust crate uses semantic versions such as `0.1.0`.

The literal profile identifier is not stored in the database. A conforming
profile-v1 vault has `vault.version = 1`. Other values are unsupported unless a
later specification defines them.
Readers determine compatibility from the migration records, the per-vault
`version`, and the persisted KDF fields. Unknown algorithms, versions, or
invalid byte lengths MUST fail closed rather than falling back to defaults.

## Complete on-disk data set

A complete live Buddy data set consists of:

```text
buddy.sqlite
attachments/
└── <vault_id>/
    └── <blob_id>        # raw encrypted attachment bytes
```

The database contains vault verifiers, encrypted entry payloads, attachment
metadata, and wrapped attachment keys. Attachment contents are not stored in
SQLite. Consequently, copying only `buddy.sqlite` can recover entry metadata
but cannot recover attachment contents; a complete recovery copy needs both the
database and the corresponding `attachments` tree.

This document describes the live format. Application-generated SQLite backup
files and interchange exports are separate containers and may not include the
external attachment tree.

## Password encoding and master-key derivation

Buddy receives a password as a Unicode string and passes its exact UTF-8 bytes
to Argon2id. Implementations MUST NOT normalize Unicode, trim whitespace,
change case, append a terminator, or pre-hash the password.

Each vault stores its own Argon2 parameters. Readers MUST use those persisted
values rather than the current creation defaults.

| Input | Profile-v1 creation value |
| --- | --- |
| Algorithm | Argon2id |
| Password | Exact UTF-8 bytes |
| Salt | 16 random bytes |
| Memory cost | 65,536 KiB |
| Time cost | 3 |
| Parallelism | 4 lanes |
| Argon2 version | 19 (`0x13`) |
| Output | 32 bytes |

The reference reader recognizes Argon2 versions 16 (`0x10`) and 19 (`0x13`)
when explicitly persisted. Current writers create version-19 vaults. The
`kdf_algo` value is the lowercase ASCII string `argon2id`.

Pseudocode:

```text
password_bytes = UTF8(password)                 # no normalization
master_key = Argon2id(
    password = password_bytes,
    salt = vault.salt,
    memory_kib = vault.kdf_mem_cost,
    iterations = vault.kdf_time_cost,
    parallelism = vault.kdf_parallelism,
    version = vault.kdf_version,
    output_length = 32,
)
```

The password, password bytes, and master key are never persisted.

## Purpose-specific keys

The 32-byte master key is input keying material for HKDF-SHA-256. HKDF has no
caller-supplied salt; under RFC 5869 this means a 32-byte all-zero salt for
SHA-256. Each expansion produces exactly 32 bytes.

| Purpose | Exact HKDF `info` bytes |
| --- | --- |
| Password verifier | UTF-8/ASCII `vault-verification-v1` |
| Entry JSON | UTF-8/ASCII `entry-key-v1` |
| Attachment key envelopes | UTF-8/ASCII `entry-blob-key-v1` |

```text
verification_key = HKDF-SHA256(master_key, no_salt,
                               "vault-verification-v1", 32)
entry_key        = HKDF-SHA256(master_key, no_salt,
                               "entry-key-v1", 32)
entry_blob_key   = HKDF-SHA256(master_key, no_salt,
                               "entry-blob-key-v1", 32)
```

The context bytes are protocol constants. Changing capitalization, spelling,
encoding, or the version suffix derives a different key.

## Password verifier

Vault creation performs these steps:

1. Generate the 16-byte Argon2 salt and derive `master_key`.
2. Derive `verification_key` with the verifier HKDF context.
3. Generate a random 24-byte nonce.
4. Generate 32 random verifier plaintext bytes.
5. Encrypt those bytes with XChaCha20-Poly1305, `verification_key`, the nonce,
   and empty associated data.
6. Persist the salt, nonce, ciphertext and tag, and Argon2 parameters.

The resulting verifier ciphertext is 48 bytes: 32 encrypted bytes followed by
the 16-byte authentication tag. The random verifier plaintext has no semantic
value and is not stored separately.

To check a password, derive the candidate master and verification keys and
authenticate/decrypt the stored verifier. Successful authentication proves the
candidate password derived the correct key. The decrypted bytes do not need to
be interpreted. Any authentication error is an invalid-password or corrupt-data
failure; implementations MUST NOT return unauthenticated plaintext.

## Authenticated encryption

Every encryption in this profile uses:

| Parameter | Value |
| --- | --- |
| Algorithm | XChaCha20-Poly1305 |
| Key | 32 bytes |
| Nonce | 24 fresh random bytes |
| Associated data | Record-specific, as defined below |
| Output | Ciphertext followed by 16-byte tag |

The verifier and attachment-content ciphertext use an empty byte string as
associated data. Entry ciphertext and attachment-key envelopes bind their
cleartext identifiers using the canonical framing below. Other cleartext
metadata, including timestamps and usage counters, is not cryptographically
bound to ciphertext in profile v1.

### Canonical record context

An authenticated record context consists of four byte-string fields:

| Protected object | Fields, in order |
| --- | --- |
| Entry payload | `buddy-vault-v1`, `entry`, `vault_id`, `entry_id` |
| Attachment-key envelope | `buddy-vault-v1`, `entry-blob-envelope`, `vault_id`, `blob_id` |

The first two fields are the exact ASCII/UTF-8 bytes shown. IDs use their exact
UTF-8 bytes. Each field is independently encoded as its unsigned 64-bit
big-endian byte length followed by the field bytes:

```text
frame(field) = U64BE(length_in_bytes(field)) || field
aad = frame(field_1) || frame(field_2) || frame(field_3) || frame(field_4)
```

The context is not stored separately. Readers reconstruct it from the profile
and the cleartext row identifiers. Substituting a ciphertext into a different
record type, vault, or record ID MUST fail authentication.

## SQLite migration 1

The database contains application tables in addition to the vault data. The
tables relevant to recovery are `migrations`, `vault`, `entry`, and
`entry_blob`.

### `migrations`

| Column | SQLite type | Meaning |
| --- | --- | --- |
| `version` | `INTEGER PRIMARY KEY` | Applied database migration |
| `created_at` | `INTEGER NOT NULL` | Application timestamp |

Migration `1` creates the remaining tables described here.

### `vault`

| Column | SQLite type | Meaning |
| --- | --- | --- |
| `id` | `TEXT PRIMARY KEY` | Cleartext vault ID |
| `salt` | `BLOB NOT NULL` | 16-byte Argon2 salt |
| `nonce` | `BLOB NOT NULL` | 24-byte verifier nonce |
| `ciphertext` | `BLOB NOT NULL` | 48-byte verifier ciphertext and tag |
| `name` | `TEXT NOT NULL` | Cleartext display name |
| `color` | `TEXT NULL` | Cleartext display color |
| `hint` | `TEXT NULL` | Cleartext password hint |
| `biometrics_enabled` | `INTEGER NOT NULL` | Application flag, zero or nonzero |
| `kdf_algo` | `TEXT NOT NULL` | `argon2id` |
| `kdf_mem_cost` | `INTEGER NOT NULL` | Argon2 memory in KiB |
| `kdf_time_cost` | `INTEGER NOT NULL` | Argon2 iterations |
| `kdf_parallelism` | `INTEGER NOT NULL` | Argon2 lanes |
| `kdf_version` | `INTEGER NOT NULL` | Argon2 version, normally 19 |
| `password_changed_at` | `INTEGER NOT NULL` | Cleartext timestamp |
| `version` | `INTEGER NOT NULL` | Last application migration applied to this vault |
| `created_at` | `INTEGER NOT NULL` | Cleartext timestamp |
| `updated_at` | `INTEGER NOT NULL` | Cleartext timestamp |

Names, colors, hints, flags, IDs, and timestamps are not encrypted by this
format. The operating-system biometric wrapping material is application state
and is not required for password-based recovery.

### `entry`

The primary key is the pair `(vault_id, id)`.

| Column | SQLite type | Meaning |
| --- | --- | --- |
| `id` | `TEXT NOT NULL` | Cleartext entry ID, scoped to the vault |
| `vault_id` | `TEXT NOT NULL` | Cleartext owning vault ID |
| `nonce` | `BLOB NOT NULL` | 24-byte entry nonce |
| `ciphertext` | `BLOB NOT NULL` | Encrypted JSON followed by tag |
| `created_at` | `INTEGER NOT NULL` | Cleartext timestamp |
| `updated_at` | `INTEGER NOT NULL` | Cleartext timestamp |
| `used_at` | `INTEGER NULL` | Cleartext last-use timestamp |
| `used_count` | `INTEGER NOT NULL` | Cleartext use counter |
| `deleted_at` | `INTEGER NULL` | Cleartext trash timestamp |

Construct the entry record context from `vault_id` and `id`, then decrypt
`ciphertext` using `entry_key`, `nonce`, and that associated data. The
authenticated plaintext is the UTF-8 JSON payload described below.

### Entry JSON payload

The top-level payload is:

```text
EntryPayload = {
  "icon": string | null,
  "groups": EntryGroup[]
}

EntryGroup = {
  "id": string,
  "name"?: string,
  "fields": EntryField[]
}

EntryField = {
  "id": string,
  "role"?: FieldRole,
  "name": string,
  "value": FieldValue,
  "history"?: FieldHistory[]
}

FieldHistory = {
  "value": string,
  "created_at": integer
}
```

Every group has a stable `id`. The ID identifies the group within its entry and
MUST be preserved when the group is edited. `name` is omitted when absent,
`role` is omitted when it is `none`, and `history` is omitted when absent.

Known `FieldRole` string values are:

```text
note, file, secret, secret_note, title, tags, username, password, url, totp,
card_name, card_number, card_cvv, card_exp, ssh_public_key, ssh_private_key,
ssh_passphrase, street, street2, city, region, postal_code, country
```

An application-preserved custom role uses Serde's externally tagged form
`{"unknown":"value"}`. Recovery readers SHOULD preserve roles they do not
understand rather than discarding their fields.

`FieldValue` is internally tagged by `type` with its payload in `value`:

```text
{"type":"string",     "value":"text"}
{"type":"string_vec", "value":["one", "two"]}
{"type":"totp",       "value":null | TotpConfig}
{"type":"file",       "value":FileRef[]}
```

```text
TotpConfig = {
  "secret": string,              # base32 text
  "issuer": string | null,
  "account": string,
  "algorithm": "sha1" | "sha256" | "sha512",
  "digits": 6 | 8,
  "period": 30 | 60
}

FileRef = {
  "blob_id": string,
  "filename": string,
  "mime_type": string | null,
  "size": nonnegative integer
}
```

The entry ID and usage timestamps live outside this encrypted payload in
SQLite. Attachment filenames, MIME types, and sizes live inside encrypted
`FileRef` values.

### `entry_blob`

The primary key is the pair `(vault_id, id)`. Each attachment uses envelope
encryption so a password change can rewrap its data key without rewriting the
potentially large attachment ciphertext.

| Column | SQLite type | Meaning |
| --- | --- | --- |
| `id` | `TEXT NOT NULL` | Cleartext blob ID, scoped to the vault |
| `vault_id` | `TEXT NOT NULL` | Cleartext owning vault ID |
| `entry_id` | `TEXT NULL` | Cleartext owning entry ID, or orphan |
| `nonce` | `BLOB NOT NULL` | 24-byte attachment-content nonce |
| `envelope_nonce` | `BLOB NOT NULL` | 24-byte data-key envelope nonce |
| `envelope_ciphertext` | `BLOB NOT NULL` | Encrypted 32-byte data key plus tag |
| `created_at` | `INTEGER NOT NULL` | Cleartext timestamp |
| `updated_at` | `INTEGER NOT NULL` | Cleartext timestamp |

Attachment encryption:

```text
data_key = random(32)
content_nonce = random(24)
content_ciphertext_and_tag = XChaCha20Poly1305(
    key = data_key,
    nonce = content_nonce,
    aad = empty,
    plaintext = attachment_bytes,
)

envelope_nonce = random(24)
envelope_ciphertext_and_tag = XChaCha20Poly1305(
    key = entry_blob_key,
    nonce = envelope_nonce,
    aad = record_context(
        "buddy-vault-v1",
        "entry-blob-envelope",
        vault_id,
        blob_id,
    ),
    plaintext = data_key,
)
```

`envelope_ciphertext` is therefore exactly 48 bytes. The attachment content
ciphertext is stored verbatim at `attachments/<vault_id>/<blob_id>` and its
nonce is the row's `nonce` value.

Attachment recovery reverses the operations:

1. Derive `entry_blob_key` from the master key.
2. Reconstruct the attachment-envelope record context and decrypt
   `envelope_ciphertext` to obtain the 32-byte `data_key`.
3. Read the external attachment ciphertext file.
4. Decrypt it with `data_key` and the row's `nonce`.
5. Match it to an entry using `entry_id` or encrypted `FileRef.blob_id`.

## Recovery order

A password-based recovery tool can process a vault as follows:

1. Open `buddy.sqlite` read-only and inspect migration records.
2. Select a `vault` row and validate all salt, nonce, and ciphertext lengths.
3. Encode the supplied password exactly as UTF-8.
4. Derive the master key using the row's KDF fields.
5. Derive the verification key and authenticate the verifier.
6. Derive the entry and attachment-envelope keys.
7. Reconstruct each entry's record context, decrypt every matching `entry` row,
   and parse its JSON payload.
8. If the attachment tree is available, unwrap and decrypt each matching
   `entry_blob`.
9. Treat any AEAD failure as wrong credentials or corrupted/tampered data; do
   not emit the unauthenticated record.

Deterministic inputs and expected outputs for password encoding, key
derivation, verifier authentication, entry decryption, and attachment-key
unwrapping are in [`../test-vectors/v1.json`](../test-vectors/v1.json).

## Security status

This specification documents the implemented format; it is not a security
proof or audit. `buddy-crypto-core` has not yet completed an independent
third-party audit. The deterministic test-vector material is public and unsafe
for production use.
